# Organisation account walkthrough

Start the application using the README commands and your explicitly chosen demo password. No public default password is supplied. New registrations require platform activation; the CLI first-administrator bootstrap is separate from the operational reviewer.

1. Sign in as `originator@demo.chakrasetu.local`. Open **My Organisation → Edit Organisation Profile**. Change the description/display name, save, refresh and verify the result. Cancel another edit and verify the saved profile remains intact. An ordinary edit should not create a verification request.
2. Upload a PNG, JPEG or WebP logo under 2 MB. Verify the directory avatar and organisation profile show it. Try a malformed image/SVG or oversized file and inspect the validation message. Replacing a logo should show the new image without a hard reload.
3. Set contact visibility to **Only my organisation and authorised reviewers**. Open another account's directory profile: its contact button must show a permission explanation instead of private values. Set visibility to authenticated participants if the business wishes to share its business email/phone. Use the eye icon to reveal then conceal; hidden values are not prefetched.
4. Add a facility with its real declared coordinates and capacity for the exercise. It remains unverified. Edit its description; this does not grant an operational capability or alter qualification. Request identity/facility review separately where required.
5. Submit an additional operational role or a facility-specific capability. No evidence upload is required at submission. Read the 48-hour response target, inspect **Pending Verification**, then refresh. The request and history must remain. The existing approved scope remains unchanged.
6. Sign out and sign in as `reviewer@demo.chakrasetu.local`. Open **My Organisation → Capability Review Queue**. Review the organisation summary, facility and requested scope. Choose **Additional Information Requested** and enter what is needed and why. The applicant can respond in the same request without starting again.
7. For a suitable scope, approve with the review reason, evidence reference and qualification expiry. The evidence is an actual review reference for your exercise, not proof supplied by the software. An operational-role approval alone does not qualify a facility, transporter or unsafe battery. The primary organisation account gains any corresponding processing/transport role when its capability is approved.
8. Return to the applicant account. Refresh: combined approved roles appear together, with their relevant navigation. There is no role selector. Try a direct hash URL to an unrelated page from a transporter-only account: it returns to Overview. The server must still reject unauthorised API calls.
9. Submit a modification to an approved scope. Confirm the operational scope remains unchanged while pending. Have the reviewer reject it: the previous approved scope persists. Suspend a reviewed scope, or request and record removal; historic requests and transaction records must remain available.
10. Open **Participant Network**. Search a name/type/location; clear filters and inspect the one-card-per-organisation directory. View declared, example and reviewed scopes with their facility. A seeded example scope is not an independently approved real-world qualification. No contacts, websites or logos are invented to fill missing fields.
11. Sign in as `buyer@demo.chakrasetu.local`: both refurbishment and diagnostics workflows are available from the same account. Historic `technician` credentials remain for backward-compatible HTTP rehearsals; new organisations do not need separate credentials for new roles.
12. Repeat the core transaction and downstream processing walkthrough in DEMO_GUIDE.md. Physical arrival alone must not change custody, pending scope must not bypass qualification, and processing completion still requires documented inputs/outputs and review.

Keyboard checks: tab through navigation, profile fields, eye controls and action buttons; confirm labels and focus remain usable. Check narrow/mobile layouts, scrolling forms, long names, map textual alternatives and API-error recovery. These real-browser checks remain outstanding in the provided environment: its browser cannot access the local process and the attempted Chromium download was invalid. Automated DOM and real HTTP checks are separate evidence, not a substitute for visual browser QA.

Persistent hosting requires both the database and `UPLOAD_DIR` on durable storage. Do not upload private real-world documents into a temporary demonstration deployment without an appropriate deployment/access arrangement.
